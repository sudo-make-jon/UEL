Universal Engineering Layer · How To

Your AI engineering system, explained.

The Universal Engineering Layer gives coding agents a shared engineering discipline, a set of task workflows, a modern tool hierarchy, and an Engineering Companion that recommends what to do next based on the current moment of the project.

Architecture

The skill stack

Always active

Karpathy Guidelines

Defines engineering behavior: understand first, keep changes surgical, surface assumptions, and verify the result.

Engineering Companion

Identifies the current project moment, estimates risk, and routes the task toward the best workflow and tools.

On demand

Provides task-specific workflows such as specification, implementation, TDD, review, prototyping, and triage.

Practical usage

How to use the Engineering Companion

Claude Code & skill-aware harnesses

Invoke the meta-skill directly

When your harness exposes installed skills as slash commands, run:

/engineering-companion

Or give it a focused request:

/engineering-companion what should I do next?

/engineering-companion assess the risk of this refactor

/engineering-companion which skill should I use for this bug?

This is the richest mode because the skill can combine your active request with project state and whatever tools the harness exposes.

Terminal

Ask from the shell

The portable repository-state detector is always available:

engineering-layer companion

or from a local copy:

./universal-engineering-layer.sh companion

The shell mode uses Git and repository signals. It does not know as much about your current conversational intent as the slash-command skill.

UEL-generated infrastructure is excluded from project-moment detection, so installing the layer itself does not look like product implementation work.

Automatic routing: compatible harnesses may also select the Engineering Companion automatically when you are clearly asking what to do next, how risky a change is, or which engineering workflow should be used.
Important distinction

how-to.html is this tutorial — not your project's PRD

This file exists only to explain the Universal Engineering Layer. The Engineering Companion is explicitly instructed not to use it as a project seed, product specification, requirements document, design brief, or source of product intent.

To understand what your project is meant to become, the agent should prefer your current request, CONTEXT.md, actual project documentation, ADRs, source code, tests, issues, and Git history.

Project awareness

Project moments

The companion re-evaluates the moment as the work evolves.

IdeaThe concept exists, but scope and constraints are still fuzzy.
DiscoveryThe repository, subsystem, or dependency needs to be understood.
SpecificationExpected behavior needs to be made explicit before coding.
PlanningKnown work should be decomposed into implementation units.
ImplementationA defined change is actively being built.
DebuggingObserved behavior differs from expected behavior and the cause is unknown.
RefactoringStructure changes while behavior should remain stable.
Testing / ReviewThe main goal becomes confidence rather than new code.
Integration / PRComponents, CI, review, or remote collaboration become the focus.
Release / Production IncidentDeployment, rollback, observability, and blast radius matter most.
Tool hierarchy

How routing works

Understand your own code

1. codebase-memory / LSP
2. ast-grep
3. ripgrep
4. manual traversal

Use the most semantic tool that can answer the question cleanly.

Understand external libraries

1. Context7
2. official docs
3. web search

Context7 is for third-party APIs, not for understanding your own repository.

Verify a change

1. focused tests
2. broader tests
3. typecheck
4. lint
5. build
6. Playwright

Collaborate

Local Git → diffs / branches / commits
GitHub MCP → issues / PRs / CI

Prefer read-only remote access by default.

Example

A typical workflow

User asks for a change

The harness reads project rules and the shared engineering layer.

Companion detects the moment

It decides whether this is discovery, implementation, debugging, refactoring, review, release, or another moment.

Karpathy baseline applies

The work stays minimal, explicit, and verifiable.

The right workflow skill is selected

Specification, TDD, implementation, code review, triage, or another relevant skill is loaded.

The right capabilities are used

Semantic code tools, external docs, structural search, browser verification, or GitHub context are used only when they add value.

Verification becomes the final moment

Tests, typecheck, lint, build, runtime behavior, and diff review close the loop.

The goal is not to force one AI tool on a project. The goal is to make the project carry its own engineering discipline, so different agents can work under the same rules.
